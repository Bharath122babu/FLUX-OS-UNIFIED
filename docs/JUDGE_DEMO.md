# Hack Day judge demonstration — FLUX//OS unified core

## Purpose

Demonstrate that a single causal memory/commit engine preserves work that did **not** depend on a changed source file and rejects work that **did**. This is different from proving general intelligence or a model-level speedup.

## Offline reproducible portion (no model key)

```bash
pip install -e ".[test]"
pytest -q
fluxos unified-demo
fluxos serve
```

In `unified-demo`, `api.py` and `styles.css` are real files. One artifact reads `api.py`, another reads `styles.css`. Changing `api.py` invalidates only the dependent artifact. The repair publishes a new artifact version. **All three phases are deterministic**, not generated by Gemma.

In the UI, the **verification and evidence** section has the legacy visually interactive deterministic experiment. The project includes both for demonstration of the causal mechanism. Its event list can be expanded.

## Model-dependent portion (requires API access)

Set `GEMINI_API_KEY`, start the dashboard and submit a small Python application goal. Gemma should make native tool calls, edit in a private candidate and return an honest `DRAFT` unless a trusted independent acceptance suite has actually passed. If configured, Docker runs tests using a separate trusted isolated-mode launcher.

Demonstrate a bounded independent delegation only when appropriate; do not fabricate parallel work or claim more than three workers.

## Judge Q&A

**What is novel?** Not MVCC or tool loops. Our research hypothesis is that program-input witnesses and one causal publication gate enable safer selective reuse of actual agent-developed outputs under requirements changes, saving model work. It has not been benchmarked yet on Gemma.

**What makes Gemma smarter?** Nothing in its weights changes. We supply better tool semantics, versioned context and rejection/repair feedback. The same model must be compared against a minimal agent with equal budgets before improvement is claimed.

**Can it run safely on hostile code?** Not production-grade. Docker isolation and trusted acceptance suite boundaries are present, but the real Docker adversarial suite and resistance to malicious Python inside the test process remain unverified.

**Is it a full autonomous developer?** It is an experimental development harness with typed file tools, bounded delegation and causal file witnesses, not a general software engineer. No JS/browser acceptance and no persistent multi-session recovery are claimed.
